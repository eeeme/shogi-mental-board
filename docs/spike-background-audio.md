# 技術検証（スパイク）: 00モードのバックグラウンド再生

対象: 00「ただ読み上げ（受動）」を、他アプリ使用中・画面ロック中でも鳴らし続ける。
結論を先に: **`speechSynthesis` では不可**。**事前生成音声 + `<audio>` + MediaSession** なら
PWAでも「画面ロック中の継続再生」はある程度可能だが、iOS Safari は制約が強く、
**完全な安定動作は Capacitor でネイティブ化してから**が現実的。買い切り版の有料機能に位置づける。

> 注意: この検証は実機での最終確認が必要です。CI/サンドボックス環境では
> iOS Safari / Android Chrome の実挙動（ロック画面・バックグラウンド）を再現できないため、
> 下記は Web 標準の仕様・既知の挙動に基づく設計と、実機確認すべきチェックリストです。

## 1. なぜ現行方式（speechSynthesis）ではダメか

- iOS Safari: 画面ロックやタブ非アクティブで `speechSynthesis` は**停止**する。復帰時も再開保証なし。
- Android Chrome: バックグラウンドで**サスペンド**されやすい。端末/省電力設定に依存。
- `speechSynthesis` は MediaSession と結びつかず、ロック画面に再生UIも出せない。
- → 「ながら聴き（画面を消して通勤中に聞く）」という 00 の主用途を満たせない。

## 2. 採用方式: 事前生成音声 + `<audio>` + MediaSession API

音声を**あらかじめ音声ファイルにして**おき、無音を挟まない1本の `<audio>` として再生し続ける。
`<audio>`（HTMLMediaElement）はバックグラウンド再生の対象になり、MediaSession API で
ロック画面に再生/一時停止コントロールを出せる。

### 2-1. 音声素材の持ち方（2案）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 18クリップ連結 | 筋9（イチ〜キュウ）＋段9（同）＝18クリップを筋→段の順に連結再生 | 素材が軽い（18ファイル） | クリップ境界の間・イントネーションが不自然になりやすい |
| B. 81マス個別 | 「ナナロク」等81マスを個別ファイルに | 1マスが自然につながる | ファイル数が多い（81） |

**推奨: まず B（81個）で自然さを確認 → 容量が問題なら A（18連結）に最適化。**
どちらが自然に聞こえるかは実機で聴き比べて決める。読みは `coords` のカタカナ読みに一致させる。

### 2-2. 音声ファイルの生成方法

自分専用なのでビルド時に一括生成する。候補:

1. **OS/ブラウザのTTSを録音**: 実機の日本語音声を録って切り出す（品質は良いが手作業）。
2. **CLIのTTSでバッチ書き出し**（推奨・自動化しやすい）:
   - macOS: `say -v Kyoko -o out.aiff "ナナロク"` → `ffmpeg` で mp3/opus に。
   - クラウドTTS（Google/Azure/Amazon Polly の日本語）でバッチ生成。
   - `coords` の全マス読み（カタカナ）を入力に、`public/audio/<file><rank>.mp3` を81本生成。
3. 生成物は `public/audio/` に置き、ビルド時に含める（PWA プリキャッシュ対象にできる）。

> 実装補助として `scripts/gen-audio.mjs`（未コミット・要TTSエンジン）で
> `coords.allCells()` を回して読みテキスト一覧を書き出せるようにしておくと差し替えが楽。

### 2-3. 再生ループの作り

- 単一の `HTMLAudioElement` を使い回し、`ended` で次マスの `src` を差し替えて `play()`。
  - iOS はユーザー操作起点の最初の `play()` 以降、同一要素の連続再生は概ね許容される。
- 発話間隔は「クリップ長 + 無音待ち」で調整（`setTimeout` ではなく `ended` 起点が安定）。
- `navigator.mediaSession.metadata` にタイトル（例「脳内盤トレーニング」）を設定し、
  `setActionHandler('play'|'pause'|'stop', …)` でロック画面操作に対応。
- `mediaSession.playbackState` を 'playing'/'paused' に同期。

本リポジトリには最小の土台として `src/lib/mediaSession.ts`（機能検出つきラッパー）を用意した。
実際の音声再生（`<audio>` 制御）と結線すればスパイクが完成する。

## 3. PWA の限界（実機で確認すべきこと）

- [ ] iOS Safari: 画面ロック中に `<audio>` が鳴り続けるか（ホームに追加したPWAとタブで差が出る）
- [ ] iOS: ロック画面/コントロールセンターに MediaSession の再生UIが出るか
- [ ] iOS: サイレントスイッチ/消音時の挙動、他アプリ音声との割り込み（audio focus）
- [ ] Android Chrome: バックグラウンド・画面オフで継続するか、通知の再生UIが出るか
- [ ] 省電力モード時の停止有無

既知の傾向: **Android Chrome は比較的安定**、**iOS Safari(PWA) は制約が残る**。
iOS で不安定な場合は「無料版は画面表示中のみ（speechSynthesis）」「買い切り版は
Capacitor ネイティブで完全バックグラウンド」という切り分けにする。

## 4. 位置づけ・段階

1. **無料版（現状）**: 画面を開いている間のみ（`speechSynthesis`）。← 既に動作。
2. **スパイク（本PR）**: `<audio>` + MediaSession の土台と本ドキュメント。実機検証は次段。
3. **買い切り版**: 事前生成音声で画面ロック中も継続（PWAで可能な範囲）。
4. **完全版**: Capacitor ネイティブ化でOSのバックグラウンド音声を正式利用。
